# DPC-AIO 1.2.0 — GitHub Publish Kit

This kit publishes the **source repository** safely and then verifies that GitHub Actions has the configuration required to build the signed enterprise release. It never stores GitHub tokens, signing passwords, keystores, or private keys in the repository.

## 1. Prerequisites

Install `git`, GitHub CLI (`gh`), and Python 3. Authenticate interactively:

```bash
gh auth login
gh auth status
```

Extract the source ZIP using password `123`, then `cd` to the extracted repository root. If this will be a public repository, choose and add a suitable `LICENSE` first; the source package intentionally does not invent a license on your behalf.

## 2. Create/import the repository

Private repository example:

```bash
tools/release/publish_to_github.sh \
  --repo OWNER/REPOSITORY \
  --create-private \
  --skip-final-preflight
```

For a deliberately public repository use `--create-public`. The helper refuses force pushes and refuses to overwrite an existing `origin` that points to another repository.

If you already created the repository on GitHub, omit the `--create-*` flag.

## 3. Configure required GitHub Actions secrets

The authoritative list of names is `docs/releases/GITHUB-SECRETS.example`.

Required secrets:

- `DPC_AIO_RELEASE_KEYSTORE_B64`
- `DPC_AIO_RELEASE_STORE_PASSWORD`
- `DPC_AIO_RELEASE_KEY_ALIAS`
- `DPC_AIO_RELEASE_KEY_PASSWORD`

`DPC_AIO_EXPECTED_SIGNING_CERT_SHA256` should normally be a repository **variable**; the workflow also accepts it as a secret.

Example commands (values stay in your shell or stdin and are sent directly to GitHub):

```bash
gh secret set DPC_AIO_RELEASE_KEYSTORE_B64 --repo OWNER/REPOSITORY < release-keystore.base64
gh secret set DPC_AIO_RELEASE_STORE_PASSWORD --repo OWNER/REPOSITORY
gh secret set DPC_AIO_RELEASE_KEY_ALIAS --repo OWNER/REPOSITORY
gh secret set DPC_AIO_RELEASE_KEY_PASSWORD --repo OWNER/REPOSITORY
gh variable set DPC_AIO_EXPECTED_SIGNING_CERT_SHA256 --repo OWNER/REPOSITORY --body "$CERT_SHA256"
```

Do **not** create `.env`/credential files inside the repository with these values.

## 4. Run the GitHub publish preflight

```bash
python3 tools/release/github_publish_preflight.py \
  --repo OWNER/REPOSITORY \
  --json-out dist/github-publish-readiness.json
```

`READY` means: Git is clean, `origin` matches the requested repository, `gh` is authenticated, the repository is accessible, the release workflow exists, the four required signing secret **names** exist, and the expected signing certificate variable/secret exists. The report never includes secret values.

If you initially used `--skip-final-preflight`, simply rerun the command above after configuring GitHub.

## 5. Run the release workflow

The release workflow is `.github/workflows/build-aio-enrollment.yml` and supports `workflow_dispatch`.

```bash
gh workflow run build-aio-enrollment.yml --repo OWNER/REPOSITORY
```

Then inspect/watch the newest run:

```bash
gh run list --repo OWNER/REPOSITORY --workflow build-aio-enrollment.yml --limit 5
gh run watch --repo OWNER/REPOSITORY
```

The build job has read-only repository permissions. Signing secrets are scoped only to the signing/build steps and the keystore is removed before the external emulator action. The separate publish job is the only job with `contents: write`.

The publish job uses the run-scoped `${{ github.token }}` supplied automatically by
GitHub Actions; no personal access token or manually configured `GH_TOKEN` secret is
required. Uploaded Actions artifact names include `github.run_id` and
`github.run_attempt`, so retries and concurrent runs cannot reuse a fixed artifact
name. The publish job resolves that same dynamic name when downloading the verified
bundle.

## 6. Evidence expected from GitHub Actions

A successful run should publish/download evidence including:

- `DPC-AIO-enterprise-release.apk`
- work-profile and Device Owner QR/JSON payloads
- `SHA256SUMS.txt`
- `build-environment.json`
- `android-runtime-smoke.json`

The `android-runtime-smoke.json` evidence is generated by the API 35 emulator Device Owner smoke test. A successful source upload alone must not be interpreted as proof that Android runtime enrollment passed.

## 7. Tag release

When you are satisfied with the continuous/workflow_dispatch build, create and push a version tag without force:

```bash
git tag -a v1.2.0 -m "DPC-AIO 1.2.0"
git push origin v1.2.0
```

The same workflow validates the signed APK/QR/runtime evidence before the tag-release publish job uploads assets.

## 1.2.0 QR Release Bundle

A successful workflow run publishes three QR entry points:

- `work-profile-qr.png` for BYOD / Profile Owner enrollment;
- `device-owner-qr.png` for Fully Managed / Device Owner enrollment from Setup Wizard after factory reset;
- `provisioning-qr.png` for the workflow-selected compatibility mode.

The release also publishes `DPC-AIO-1.2.0-QR-RELEASE-BUNDLE.zip`, `DPC-AIO-1.2.0-QR-RELEASE-BUNDLE.zip.sha256`, `QR-README.md`, `RELEASE-INDEX.json`, and `SHA256SUMS.txt`. QR assets are created only from the signed release APK and its final public release URL.
