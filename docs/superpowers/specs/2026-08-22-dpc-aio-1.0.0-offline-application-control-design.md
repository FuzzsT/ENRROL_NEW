# DPC-AIO 1.0.0 Offline & Application Control — Design

## Status
Approved by user on 2026-08-22 after four section reviews.

## Goal
Evolve DPC-AIO 0.9.0 into DPC-AIO 1.0.0 with a real full-offline deployment path, a per-application Permission Manager 2.0, and an Activity/Component Manager 2.0 that can enable, disable, or restore component state only through capabilities actually available on the device.

## Source basis
The design was informed by static analysis of user-supplied `4.zip`, especially Android ManagedProvisioning (`Praca 16`) for offline provisioning flow, Samsung Smart Switch for permission/component-management patterns, and system applications using `PackageManager.setComponentEnabledSetting()`. Private Samsung APIs and undocumented privileged contracts are reference material only and are not copied into production code.

## Project-wide constraints
- One monolithic DPC APK remains the product model.
- `Show Hidden` exposes unsupported capabilities/statuses but never enables an unsupported operation.
- `Developer/Lab` remains separate from production-safe functionality.
- Public Android Enterprise / PackageManager / PackageInstaller APIs are the primary routes.
- Shizuku is optional, explicit, and capability-gated; it is never treated as equivalent to DevicePolicyManager ownership.
- No reflection-based arbitrary method execution, no `trustAllCertificates`, no signature bypass, no hidden/private Samsung service imitation.
- All state-changing operations follow Preview -> Apply -> Readback -> VERIFIED/MISMATCH.
- Full offline mode performs no backend/DNS/HTTPS calls until the mode explicitly transitions to sync.
- Offline bundles contain no private signing key. The app embeds only public verification material.
- Critical DPC components cannot be disabled by normal Component Manager flows.

## 1. Full Offline Engine

### Enrollment modes
Introduce:
- `ONLINE`
- `ONLINE_PREFERRED`
- `FULL_OFFLINE`
- `OFFLINE_THEN_SYNC`

`FULL_OFFLINE` is a hard no-network execution mode. `OFFLINE_THEN_SYNC` may transition to a later bounded sync job after local provisioning succeeds.

### Offline readiness
A readiness evaluator must verify:
- DPC availability/state;
- supported Android API and provisioning mode;
- offline bundle signature and hash integrity;
- bundle schema and DPC-version compatibility;
- required package presence and package-file hashes;
- capability support for requested permission/component/policy operations.

The result is one of `FULL_OFFLINE_READY`, `OFFLINE_PROFILE_INCOMPATIBLE`, or a precise blocking code such as `OFFLINE_PACKAGE_MISSING`.

### Signed offline bundle
Canonical bundle layout:

```
offline-bundle/
  manifest.json
  manifest.sig
  policies/<profile>.json
  packages/<package>/base.apk
  packages/<package>/split_*.apk
  metadata/package-index.json
```

Manifest fields include `schemaVersion`, `bundleId`, `organizationId`, `minimumDpcVersion`, `minimumAndroidApi`, `allowedModes`, policy path, package names, version codes, SHA-256 hashes, and signing-certificate SHA-256 identities.

Verification order:
1. manifest bytes/hash;
2. detached signature;
3. schema/version/mode compatibility;
4. package files and split completeness;
5. package hashes;
6. package signing identities when Android package inspection is available;
7. requested capability validation.

### Offline Package Vault
Support local import via Storage Access Framework and private app storage. The vault tracks bundle/package verification status, base/split completeness, and install planning.

### Package installation
Use `PackageInstaller` for local APK/split APK installation. On supported APIs, allow a parent multi-package session for atomic package-set commit. Otherwise use sequential installation with explicit readback. Silent installation is exposed only where the device-owner/affiliated-management context actually permits it; user action is preserved when Android requires it.

### Offline transaction
Stages:
- `BUNDLE_RECEIVED`
- `BUNDLE_VERIFIED`
- `PACKAGES_STAGED`
- `PACKAGES_INSTALLED`
- `PERMISSIONS_APPLIED`
- `COMPONENTS_APPLIED`
- `POLICIES_APPLIED`
- `READBACK_VERIFIED`
- `OFFLINE_VERIFIED`
- `SYNC_PENDING`
- `SYNCED`
- `FAILED`

A critical mismatch never becomes `COMPLETE`.

## 2. Permission Manager 2.0

### Permission inventory model
Each per-app record separates:
- manifest/requested state;
- actual PackageManager grant state;
- DPC grant state;
- AppOps state;
- target user/profile;
- permission group/protection;
- execution route and capability.

### Control states
Runtime-permission DPC states are exactly:
- `DEFAULT`
- `GRANTED`
- `DENIED`

Global future-request policy supports:
- `PROMPT`
- `AUTO_GRANT`
- `AUTO_DENY`

### Execution routing
Resolver priority is deterministic and capability-based:
1. DevicePolicyManager or delegated permission-grant route;
2. explicitly authorized Shizuku route;
3. system-privileged route;
4. user settings/action;
5. unavailable.

No try-everything loop is allowed.

### Sensor/restricted guard
The capability resolver accounts for ownership type, API level, provisioning sensor-grant opt-out, and restricted/sensor permissions. Unsupported grant operations are disabled before apply.

### Batch and rollback
Batch workflow:
- inventory snapshot;
- preview each item and route;
- apply supported items;
- per-item readback;
- result summary;
- optional restore of prior DPC-managed states only.

### AppOps and special access
AppOps and special-access states are modeled separately from runtime permissions. They may be read-only when no legitimate control route exists.

### Local audit
Store bounded local audit entries containing timestamp, package, user, permission, previous/requested DPC state, route, operation result, and readback state. Do not upload automatically.

## 3. Activity / Component Manager 2.0

### Component inventory
Primary UI focuses on Activities, with Developer/Lab exposure for receivers, services, providers, and activity aliases.

For every component track:
- manifest enabled flag;
- override state (`DEFAULT`, `ENABLED`, `DISABLED`);
- effective enabled state;
- exported flag;
- required permission;
- target user;
- risk/protection status.

### Component operations
Normal Activity operations are:
- `ENABLE`
- `DISABLE`
- `RESTORE_DEFAULT`

### Execution routing
- Own-UID components: direct PackageManager route.
- API 33+ same-UID batches: `setComponentEnabledSettings()` where valid.
- Foreign components: only authorized Shizuku or real privileged/system route.
- Otherwise: `COMPONENT_CONTROL_UNAVAILABLE`.

DevicePolicyManager is not represented as an API for arbitrary foreign component-state control.

### Protected components
The following DPC-critical component classes are protected from normal disable actions:
- `AioDeviceAdminReceiver`
- `ProvisioningModeActivity`
- `PolicyComplianceActivity`
- `EnrollmentRecoveryReceiver`
- `EnrollmentRecoveryJobService`

System-critical targets receive HIGH/CRITICAL risk classification and require explicit review. There is no bulk “disable all system components” action.

### Multi-user and batch
Every request includes `targetUserId`. Batch may be atomic only when the underlying platform API provides atomic application; otherwise the result is marked `BATCH_NOT_ATOMIC` and verified item-by-item.

### Snapshots
Before batch changes, preserve previous override states and support restore of those overrides. Never modify APK manifests.

## 4. Integration: Application Control Center

The app presents one Application Control surface with tabs/sections for:
- Overview
- Permissions
- Activities
- Services/Receivers/Providers/Aliases in advanced mode
- AppOps
- Special Access
- Policies

Permission and component managers share inventory/user selection but retain separate capability routers.

## 5. Offline profile integration

Offline policy schema may request:
- default permission policy;
- per-package permission DPC states;
- component override states;
- package installation set;
- bounded existing device policies.

Before apply, each request is resolved to a concrete capability. Unsupported critical requests make the profile incompatible; optional unsupported requests appear in preview as skipped with a reason.

## 6. Recovery and sync

Persist offline deployment state in device-protected storage. Persist PackageInstaller session IDs when needed. Recovery receiver/job only schedules bounded work; it does not perform network or heavy package operations directly in a broadcast receiver.

`OFFLINE_THEN_SYNC` emits a bounded redacted receipt containing bundle/version/digests and enrollment identifiers, then uses the existing 0.9 server trust model for sync. The server cannot submit arbitrary reflection/script commands.

## 7. UX

Add an Offline Setup center with:
- mode selection;
- bundle import/verification;
- readiness report;
- package vault inventory;
- deployment preview;
- progress/stage state;
- recovery status;
- redacted diagnostics export.

Permission Manager 2.0 must show actual state, DPC state, AppOps, route, capability, and readback. Component Manager 2.0 must show manifest/override/effective states and explicit target user.

## 8. Capability/status additions

Permission statuses include:
`PERMISSION_NOT_REQUESTED`, `NOT_RUNTIME_PERMISSION`, `OWNER_REQUIRED`, `DELEGATION_REQUIRED`, `SENSOR_GRANT_RESTRICTED`, `PROVISIONING_SENSOR_OPT_OUT`, `SHIZUKU_REQUIRED`, `USER_ACTION_REQUIRED`, `APP_OP_CONTROL_UNAVAILABLE`, `TARGET_USER_UNAVAILABLE`, `POLICY_READBACK_MISMATCH`.

Component statuses include:
`COMPONENT_CONTROL_AVAILABLE`, `COMPONENT_CONTROL_UNAVAILABLE`, `OWN_UID_COMPONENT`, `SHIZUKU_COMPONENT_CONTROL`, `SYSTEM_COMPONENT_CONTROL`, `COMPONENT_NOT_FOUND`, `PROTECTED_DPC_COMPONENT`, `CRITICAL_SYSTEM_COMPONENT`, `COMPONENT_STATE_MISMATCH`, `BATCH_NOT_ATOMIC`.

Offline statuses include:
`FULL_OFFLINE_READY`, `OFFLINE_PACKAGE_MISSING`, `OFFLINE_BUNDLE_INVALID`, `OFFLINE_PROFILE_INCOMPATIBLE`, `OFFLINE_POLICY_PARTIAL`, `OFFLINE_VERIFIED`, `SYNC_PENDING`, `SYNCED`.

## 9. Release verification matrix

Source/host gates must cover:
- signed/tampered offline bundle verification;
- wrong package hash and missing split detection;
- offline no-network hard gate;
- permission inventory/routing/sensor restrictions/global policy;
- permission batch/readback/restore;
- component enable/disable/default;
- protected DPC components;
- multi-user routing;
- component batch atomic/non-atomic result semantics;
- offline recovery;
- redacted sync receipt;
- existing 0.9 enrollment regression suite.

Release statuses remain independent:
- `SOURCE_VERIFIED`
- `APK_BUILD_VERIFIED`
- `ANDROID_OFFLINE_VERIFIED`
- `DEVICE_OWNER_OFFLINE_VERIFIED`
- `WORK_PROFILE_OFFLINE_VERIFIED`
- `PACKAGE_INSTALL_VERIFIED`
- `PERMISSION_MANAGER_VERIFIED`
- `COMPONENT_MANAGER_VERIFIED`
- `SYNC_VERIFIED`

No live-device status is inferred from source tests.
